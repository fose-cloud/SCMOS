# SCMOS AI security boundary

Phases B/C, 2026-09-07.

- Credentials: reuse existing API-side `OpenAI__ApiKey`. No browser secret, local copy, key provisioning or live billing/quota validation. The adapter uses the existing configured model and rejects non-HTTPS custom endpoints.
- Identity: `IUserAccessor` remains authoritative. Unknown request properties are rejected, including role, user, owner and model overrides. Unrecognized accounts and unknown role names fail closed; carriers have no internal adapter.
- Scope: use the existing `ViewTeam` capability. Without it, a blank OperatorId refuses the request rather than implying all records. This does not change legacy route policies. Supplier/rate/incident/compliance-specific projection still needs review before those agents activate.
- Injection: system instructions and user text use distinct SDK roles. Tool output is untrusted; only offered names and valid typed arguments can become proposals. No raw SQL, shell, arbitrary URL fetch or model-owned execution. Phase B mock ignores operational instructions and reads no records. This is not a claim that prompt wording alone prevents injection in later retrieval flows.
- Execution: three explicit read handlers are connected. There is no write dispatcher, approval executor or external communication. A flag cannot authorize a write or replace durable audit. Existing legacy approval functionality is intentionally not rewired.
- Validation: reject oversized and malformed requests before provider work; body byte bound covers chunked uploads. Unknown agent/page hints are rejected. Provider refusals, unexpected tool calls, malformed arguments, truncated/empty output and provider errors do not become successful facts.
- Failure isolation: feature flags default off. Core routes and document extraction do not depend on new AI configuration or availability. The legacy gateway constructor remains unchanged. New diagnostics expose booleans, not configuration values or provider exception bodies.
- Resource controls: bounded provider cancellation/output, no automatic SDK retries, four concurrent mock runs and 20 starts/minute per instance with no queue. These are local-process controls, not distributed quotas; review before scale-out. Cancellation from the caller is propagated.
- Mock: only ASP.NET Development; independently enforced by runtime and provider. Responses visibly say `[DEVELOPMENT MOCK]`, with no fake SCMOS metrics. Production mock requests fail closed.
- Logging: only transient run ID, specialist, elapsed time and mock marker. No prompt, response, hidden reasoning, provider exception, secret, phone or email is logged by this foundation. This is diagnostic telemetry, **not** persistent audit evidence.

Phase C adds SQL-before-materialization owner filtering and a second service-level check, including malformed records. The provider receives the user request and schemas only, never retrieved records. Totals and recommendations are composed from existing SCMOS rules; a source failure is unavailable, not an empty success. Fake provider proposals for writes, unknown tools, foreign owners, oversized limits and unsupported queries are tested through the same authorization path.

Phase D IAiExecutionAudit persists server identity/scope, configured model, timestamps, tool/run status, known view/limit, source keys, computed counts and usage via SqlAiExecutionAudit. It stores no prompts, raw arguments/search text, model output, hidden reasoning, credentials or free-form exception messages. User IDs and job references remain sensitive metadata, not anonymous information. Existing ViewAudit plus known internal identity gates list/detail reads in endpoint and service; no permission grants were changed.

Audit start commits before provider access and before each read; completions commit before evidence release. An isolated context cannot save pending business entities. Exact event retries are idempotent; conflicting metadata, reordered/orphan tool events, changed actors/scopes and fabricated completion totals are refused. The checksum detects conflicting retries, not malicious DB-admin tampering. SQL data persists across connections, but this is not WORM storage. There is no API to update/delete audit rows, no automated retention job, and migration Down always refuses; rollback disables AI and preserves evidence.

Source/provider failures record allowlisted status codes. Cancellation cleanup uses an independent two-second token; partial histories remain visible as incomplete after two minutes without being rewritten as success. A DB outage can prevent terminal recording; the API withholds evidence and preserves whatever was committed. A successful terminal event is backend completion, not HTTP-delivery proof. Default-off and mock execution require no SQL readiness. Preflight denied/disabled requests and mocks are not durable agent executions; existing document extraction and legacy invoke are not retroactively covered.

OpenAI Docs was used to distinguish provider retention from SCMOS audit retention. Minimizing our own stored metadata does not configure or prove Zero Data Retention at the provider; no provider retention setting was changed. See [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data). No hidden reasoning or raw chat storage is required for this implementation.

Phase E adds only an authenticated Control Tower frontend. Same-origin apiFetch retains the existing proxy identity boundary; no credential is rendered or stored in the client. The request builder accepts a bounded message with fixed Operations context, never user/role/owner/model/tool overrides. Prompt/evidence/Audit state is memory-only and discarded when relevant identity/capability scope changes. Safe error allowlists and React text rendering prevent raw upstream error/HTML display. The client validates evidence totals, source labels and caps, and never substitutes zero for a failed/unavailable measure. These controls supplement, not replace, server authorization.

Dashboard/briefing reads require ViewDashboard and Audit reads require ViewAudit. Carriers cannot open the internal screen. Source actions navigate existing read views; they do not invoke legacy approval/write APIs. A missing Monitor permission routes the reader to My Job instead. Readiness is metadata, not proof of provider connectivity. Synthetic fixture data exists only under tests and is not imported by production UI. Initial desktop automation failed; the 2026-09-08 isolated Edge headless checks subsequently verified capability-dependent requests, carrier exclusion, sanitized errors, cancellation and mock isolation. Synthetic identities do not prove actual Entra/proxy authorization or production browser security.

Outstanding release gates: review all pending migrations against fresh live history, migration/deployment approval, live provider/source smoke tests, production latency measurement, retention/archival decision and signed-in production verification. Phase D has actual isolated LocalDB persistence/failure/cancellation tests, not production integration proof. Later write tools need exact-payload approval, business authorization, audit and concurrency/duplicate-execution controls. Existing approval-list visibility and old RiskService blank-owner/date issues remain documented in Phase A.
